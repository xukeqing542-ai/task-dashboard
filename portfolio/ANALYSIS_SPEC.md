# 增长指标需求单与埋点字典（个人演示方案）

**需求场景**：运营希望每日看到用户活跃、订单转化、GMV，按渠道排查波动。输入为本项目生成的本地 CSV，不能代表公司的取数需求、生产埋点或实际部门协作。

## 业务问题拆解和验收

| 业务问题 | 数据问题／交付 | 验收标准 |
|---|---|---|
| 活跃和交易是否变动 | 每日 DAU、订单、GMV，七日 GMV 移动均值 | 日报覆盖 90 天；订单、GMV 与原始有效记录一致 |
| 哪个渠道需要排查 | Search／Direct／Social 的活跃用户日、订单及转化率 | 渠道订单／GMV 合计与日报一致；不累加跨渠道去重用户 |
| 留存是否变化 | 当日活跃集合与次日活跃集合求交，按日计算 D1 | 最后一天无次日观察，不纳入加权留存分母 |
| 异常如何定位 | 看日级变化、渠道构成、缺失／重复事件 | 保留异常样本和口径；报告仅提出调查项，不能推断因果 |

## 埋点需求草案

| 字段／事件 | 类型 | 口径与校验 | 责任边界 |
|---|---|---|---|
| `event_id` | 字符串 | 全局唯一，不为空；重复拒收 | 客户端／采集端需生成唯一 ID；本项目仅离线检查 |
| `event_date` | ISO 日期 | 事件所属自然日；同一报表统一时区 | 上线前需确认时区与迟到事件窗口 |
| `user_id` | 字符串 | 非空；用来求 DAU 和相邻日交集 | 生产环境需明确匿名 ID、登录合并和隐私规则 |
| `channel` | 枚举 | Search、Direct、Social；枚举外拒收 | 真实场景需定义归因窗口、未知来源与渠道变更 |
| `is_order` | 整数 | 0/1；本演示每人每日最多一条记录 | 真实场景应有独立订单事件与去重订单号 |
| `gmv_cny` | 数值 | 非负；`is_order=0` 时须为零 | 真实场景需定义退款、税费、币种与订单取消 |

**上线前必须补的验收项**：事件到达延迟分布、跨天去重、用户身份合并、订单／支付状态、退款回冲、内部测试流量、历史口径变更与权限控制。上述项目未在当前演示数据里实现，不能写成已上线能力。

## 分析结论和复盘入口

本次有效记录 6,202 行，原始 6,203 行，拒收重复事件 1 行；累计订单 449 笔，GMV 51,622.05 元。三个渠道的转化率（订单／活跃用户日）依次为 Search 9.26%、Direct 6.99%、Social 5.43%。渠道差异只用于演示排查顺序；没有随机分配或因果识别，不能得出“调整预算会提高成交”的结论。

建议在真实环境先和业务方确认渠道归因、GMV 与退款口径，再评估是否分层做实验。个人项目没有实际落地和后续效果数据，复盘仅检查口径、质量规则及可重复运行结果。
